## dev 那次"字符标错"事件（重要方法论记录）

dev 第一次发合并报告（9-15 凌晨）时，把 5 个 unicode 码点对应的字标成了**字形相近的另一字**：

| 码点 | 报告写的 | 实际 | 与之混淆的字 |
|---|---|---|---|
| U+52A9 | 功 | **助** | 功=U+529F |
| U+9760 | 闇 | **靠** | 闇=U+95B5 |
| U+5E2E | 差 | **帮** | 差=U+5DEE |
| U+558A | 啊 | **喊** | 啊=U+554A |
| U+6DF3 | 湳 | **淳** | 湳=U+6E33 |

**结论**：不是工具 bug。证据：

1. CSV `character` 列按 `chr(codepoint)` 直接写入（Python 实证）—— 不走任何查找表
2. 19 个字里只有 5 个错，且 5 个毫无规律地分布在两个会话 —— 工具 bug 应该全部错或某连续码段错
3. 错的 5 个恰好都是**人类容易混淆的字形**（助/功、靠/闇、帮/差、喊/啊、淳/湳）

**方法论教训**（我自己的）：

- 我看到"标错"直接跳到"码点偏移"假说，**没先列全可能原因**（编码/查找表/形近字混淆/字体回退/手抄错误）
- 正确的诊断顺序：① 先列全可能类别 ② 再问"哪种最可能" ③ 最后再行动
- 下次遇到类似错，第一步应该是**"是不是手抄/形近字混淆"**这种最简单解释

dev 的保证：

- 不再在消息文本里手抄 unicode → 汉字
- 需要向人类读者介绍字符含义时，明确说"这个 codepoint 在 CSV 里的 character 字段是 X"，不自己写

## 重建过程

只跑了 5 分钟：

```bash
# base 字体（1450 字）
python scripts/build_personal_ttf.py
# 输入：G:\...\data\sessions\all_characters (3140 PNG)
# 唯一字符数：1450
# 输出：font\my_personal_font.ttf (14,379,748 bytes)
# 校验：family=我的书法, unitsPerEm=2048, advance=[2048], lsb==xMin ✓

# 变体字体（1450 主 + 1690 PUA）
python scripts/build_variant_ttf.py \
    --base-ttf font/my_personal_font.ttf \
    --images-dir "G:\...\data\sessions\all_characters" \
    --out font/my_personal_font_variants.ttf \
    --map-out font/variant_map.json

```
